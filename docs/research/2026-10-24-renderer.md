# Renderer for a 25-minute 1080p30 Arabic animatic (~45,000 frames)

Research date: 2026-10-24. Target: deterministic frame rendering, per-element stroke write-on (`draw`), Arabic text that keeps its shaping, audio locked to 30 fps.

Machine used for all measurements: Linux 7.2.9-zen, 8 cores, 15 GB RAM, Arch. Chromium 153.0.8010.52 (system), ffmpeg 9.0.2, Node 26.11.1. Everything below marked **verified** was run here; **inferred** means read from source/docs but not executed; **unknown** means I could not establish it.

---

## 1. Decision

**Default: Remotion 4.0.538 as the frame harness, driving `exportToSvg()` output per scene, with `draw` implemented as per-element attribute animation (dash offset for outlines, clip-rect wipe for text/freedraw fallback), encoded and muxed by Remotion's own ffmpeg.**

**Fallback: Playwright (`playwright-core`) against system Chromium + manual ffmpeg mux.** Same page contract, same SVG, same per-frame attribute writes. Drop to this if (a) the project's headcount makes Remotion's Automators licence apply and $100/mo is unacceptable, (b) Remotion's webpack bundler breaks on the Excalidraw fork, or (c) you need to pin a Chromium build other than Remotion's.

**Do not use**: resvg/node-canvas (already ruled out), or SMIL as the *authoring* format with a bespoke capturer (option 3 as a standalone) — it works and is deterministic, but you rebuild Remotion's frame loop, progress, retry and mux to save a dependency you are allowed to use for free at ≤3 people.

Why Remotion wins on the numbers, not on taste:

- **3.2× faster capture path.** Remotion ships a patched Chromium 157 headless shell that returns raw frames over shared memory (`remotionFrameSlot`/`remotionFrameId` in `Page.captureScreenshot`). With a stock system Chromium the same composition renders at 117 ms/frame; with Remotion's browser, 36.3 ms/frame. **Verified by measurement, both paths.**
- **Byte-identical output across separate processes** once element seeds are fixed. **Verified.**
- **Audio mux is one command**, and the resulting container is exactly 90 frames / 3.000 s at 30/1. **Verified.**
- **Free at ≤3 people**, including commercial use. Above that, $100/mo flat if you build an automation. Details in §5.

Why the *hybrid* (exportToSvg once per scene, mutate per frame) is inside the recommendation rather than an alternative: re-running `rough.js` + perfect-freehand + React reconciliation for every one of 45,000 frames is wasted work. Export once per scene, then per frame write 2 attributes per element.

| Path | Wall time |
|---|---|
| Remotion @ 27.5 fps | **~28 min** + ~5 s startup |

LogRocket, 2026-07-23: 900 frames (30 s) rendered in ~40 s → ~22 fps; a heavier 750-frame composition took ~2.5 min → ~5 fps. Brackets my 13–73 fps range. **Verified as a published claim**, not re-run.

## 3. The `draw` transition, element by element

This is the section that decides the renderer: `draw` is not one technique, it is four, and one of them (text) is where Arabic breaks every existing tool.

### 3.1 What `exportToSvg` actually emits (Excalidraw 0.18.1)

Read from `dist/dev/chunk-4FTI6OG3.js` in the published tarball. **Verified by source.**

- One `<g transform="translate(...) rotate(...)">` per element, appended in element order (`addToRoot`). Element *i* in the array ↔ *i*-th `<g>` in the SVG. excalidraw-animate relies on exactly this and throws `element length mismatch` when it breaks.
- Rough geometry is a pure function of `element.seed` + geometry (`roughjs` 4.6.4). Same seed ⇒ same path, byte for byte.
- Shapes with a background emit **two** paths inside the `<g>`: fill first, stroke second. Frames/magicframes can add clip-path wrappers, which is the one case where "i-th `<g>`" indexing breaks.
- `exportToSvg({ elements, appState, files, skipInliningFonts })` and `exportToBlob` exist and work in a browser bundle. **Verified by rendering.**
- Default font handling: `generateFontFaceDeclarations()` inlines each registered face as base64 `@font-face` into `<defs>`. The shipped font set is `Assistant, Cascadia, ComicShanns, Excalifont, Liberation, Lilita, Nunito, Virgil, Xiaolai` — **no Arabic face**. `skipInliningFonts: true` is the escape hatch when you load the face yourself. **Verified by source + assets.**

### 3.2 Outlines (rectangle, ellipse, diamond, line, arrow, and the stroke half of any shape)

`pathLength="1"` + `stroke-dasharray="1"` + `stroke-dashoffset = 1 − p`.

- Set `pathLength` once at export; per frame write only `stroke-dashoffset`. One string write per element. **Verified** — this is exactly excalimate's `setGeometryPoster()` (`packages/export-runtime/src/animatedSvg.ts:471`) and `svgAdapter.ts:126`.
- Target the **stroke** path (`<g>` child 1 when a fill exists, child 0 otherwise). Applying dashoffset to a hachure fill path animates every hatch line at once — visually wrong. excalidraw-animate splits these: outline for 75 % of the duration, fill for the last 25 % (`patchSvgRectangle`). **Verified by source.**
- Arrow heads are separate `<path>` children. Either give them the tail 25 % of the parent's progress, or reveal the shaft to 75 % then pop the head. excalidraw-animate weights by child count: `3/(n+2)` for the shaft. **Verified by source.**
- Do **not** use SMIL `attributeName="d"` interpolation (the excalidraw-animate approach). It is correct, but it regenerates a path string per keyframe and cannot be seeked cheaply. Dash offset is strictly better for shapes. **Verified** — the `d`-morph code in `animate.ts` is `animatePath`/`animatePolygon`; it exists only because excalidraw-animate produces standalone SVG with no JS.

### 3.3 Freedraw — the trap

Excalidraw exports a freedraw element as **one filled path, not a stroked one**:

```js
// dist/dev/chunk-4FTI6OG3.js, case "freedraw"
node.setAttribute("stroke", "none");
path.setAttribute("fill", element.strokeColor);
path.setAttribute("d", getFreeDrawSvgPath(element));
```

and `getFreeDrawSvgPath` runs perfect-freehand:

```js
{ simulatePressure, size: element.strokeWidth * 4.25, thinning: 0.6,
  smoothing: 0.5, streamline: 0.5, easing: t => Math.sin(t*PI/2) }
```

**Verified by source, and confirmed visually**: in my end-to-end Remotion render, the freedraw squiggle stayed a solid blob while its `stroke-dashoffset` changed — dash offset does nothing on a fill.

Three workable techniques, in order of preference:

1. **Precompute prefix paths at build time.** For K steps (60–120 is plenty at 30 fps), call `getFreeDrawSvgPath({...el, points: el.points.slice(0, i)})` and store the `d` strings next to the board. Per frame: set `d`. Deterministic, no runtime cost, exactly the pencil-drawing look. This is excalidraw-animate's `patchSvgFreedraw` idea, moved offline so it isn't O(n²) inside the frame loop. **Verified that the API accepts a sliced element** — that is what `patchSvgFreedraw` does.
2. **Clip wipe along the stroke.** A clip path with a moving rect or a fat round-cap stroke on the element's centerline. Cheap, direction-correct, looks like a reveal rather than a pencil. Uniform with the text technique below.
3. SMIL `d` morph (excalidraw-animate): works, but you are back to path-string animation and it cannot be seeked without re-running the whole SMIL tree.

**Unknown**: how a fork that mutates freedraw storage (e.g. pressure handling changes) affects prefix-path caching. Cache key should be `(element id, points hash, strokeWidth)`.

### 3.4 Text — where Arabic breaks

Export shape: **one `<text>` element per stored line**, with
`x = textAlign==="center" ? width/2 : textAlign==="right" ? width : 0`,
`text-anchor = center ? "middle" : (right || isRTL) ? "end" : "start"`,
`direction = isRTL ? "rtl" : "ltr"`, `style="white-space: pre"`.
Line breaks are frozen in `element.text` at authoring time, so the renderer never reflows. **Verified by source.**

Consequences:

- **Shaping and bidi work in Chromium.** Rendered `مرحبا بالعالم` through `direction="rtl" text-anchor="end"` and got correctly joined cursive glyphs at the expected anchor. **Verified visually** (`/tmp/opencode/arabic-anchors.png`).
- **excalidraw-animate cannot draw Arabic text at all.** `animateText()` checks `text-anchor`; if it is not `"start"` it falls back to an opacity fade and returns. Every RTL line exports with `text-anchor="end"`. So the prior-art tool fades all Arabic instead of writing it. **Verified by source.** Its `textPath` trick is also wrong for Arabic even if forced: SVG `textPath` lays glyphs in logical order with no bidi reordering, so the run comes out mirrored and loses joining at chunk boundaries.
- **Right-aligned RTL boxes export shifted.** With `direction="rtl"`, `text-anchor="end"` puts the run's *left* edge at `x` (measured: `rtl+end@800` → bbox `x=800, w=150`; `ltr+end@800` → `x=650, w=150`; `rtl+start@100` → `x=-50`). Excalidraw emits `x=element.width` for `textAlign="right"`, so a right-aligned Arabic box renders at `[width, width+w]` — entirely outside its own box. The canvas path (`ctx` with `canvas.setAttribute("dir","rtl")` + `textAlign`) does *not* have this bug. **Verified geometry; UI reachability inferred** (the alignment buttons are left/center/right regardless of direction). This is a real candidate for the fork's fix list, next to fonts and wrapping.
- **The write-on that actually works for Arabic: a directional clip wipe per line.** A `<clipPath><rect></clipPath>` on the `<text>`, rect growing right→left for RTL, left→right for LTR, lines staggered by ~80–120 ms. Geometric, shaping-agnostic, one attribute per line per frame. **Verified**: seeking a SMIL-animated clip rect produces progressive frames and LTR/RTL wipes converge to the same final frame (`smil-clip3.mjs`).
- Alternate, only for Latin: per-word opacity, or per-character clip steps. Both destroy joining if applied per glyph to Arabic — do not.

### 3.5 Timing model (shared by every option)

- Cue times live in ms in the project file; frame = `Math.round(ms * 30 / 1000)`. Never convert the other way at render time.
- Scene duration in whole frames; composition length = `ceil(narrationMs * 30 / 1000)` + tail frames.
- Per element: `start = cueFrame`, `dur = drawDurationFrames` (default 12–20 for shapes, 8–12 per text line), `p = clamp((frame − start)/dur, 0, 1)`, then ease (`easeOutCubic` reads as handwriting; keep it one easing for the whole film).
- Element order is the authoring order (or an explicit `animateOrder` encoded in the element id, which is excalidraw-animate's convention — worth copying).

## 4. The four options compared

### (1) Remotion 4.x

**What it is, mechanically.** React frame clock + its own Chromium **157** headless shell (98.9 MB download, 236 MB extracted) + a patched `Page.captureScreenshot` that returns raw shared-memory frames instead of base64 PNG + ffmpeg encode/mux in-process. **Verified from `@remotion/renderer/dist/screenshot-task.js` and by `npx remotion browser ensure`.**

**Determinism.** `useCurrentFrame()` is an integer, and rendering is byte-identical across separate `npx remotion render` invocations after fixing element seeds: 10/10 PNG frames identical (md5) between two cold runs. **Verified.** Without fixed seeds, 0/10 matched — because `convertToExcalidrawElements()` generates a fresh `seed`/`versionNonce` per call, and rough.js derives every path from the seed. **Verified.** This is a project-level trap independent of renderer: seeds must be stable in the board file, not generated at render time.

**Fonts.** `@remotion/fonts` `loadFont({ family, url: staticFile('arabic.ttf') })` blocks the render until the face is ready, so no `delayRender` plumbing is needed. **Verified** (used it; the render produced shaped Arabic). For the fork, two modes: `skipInliningFonts: true` + `loadFont()` (in-browser only), or keep inlining and have the fork emit base64 woff2 (standalone SVG stays portable). Use the second if the exported SVG is also a deliverable.

**Arabic.** Fine, end to end, including the right-anchoring quirk above (which is Excalidraw's, not Remotion's).

**Throughput.** 36.3 ms/frame / 27.5 fps at 200 elements; 13.7 ms/frame floor. 45,000 frames ≈ 28 min. 1.6 GB peak RSS for the render process.

**Licensing — the numbers, from the licence FAQ (accessed 2026-10-24), verified:**
- Free for an individual, and for an organisation or team of **up to 3 people**, commercial use included, no signup.
- Above 3 people: **"Remotion for Creators" $25/month per person** who writes Remotion code, **or "Remotion for Automators" $0.01 per render with a $100/month minimum**. An "automation" is anything that calls `renderMedia()`, `renderFrames()`, `npx remotion render`, or even renders with `<Player>`. 1 render = 1 finished video, and **an image sequence counts as one render regardless of frame count**.
- So this pipeline (an automation) costs a >3-person shop **$1,200/year flat**, not per-seat. That is cheap next to 28 minutes of an 8-core box per draft, but it is a recurring cost tied to a dependency whose licence is not OSI-approved, and **Remotion 5.0 will make telemetry mandatory for Automators customers** (stated in the FAQ). Telemetry in client-side rendering is already non-disableable.

**Integration risks, measured:**
- Install: 89 s, 261 MB `node_modules`, +236 MB browser. Adding `@excalidraw/excalidraw@0.18.1`: 16 s, 49 MB.
- **Bundling breaks on roughjs.** Excalidraw 0.18.1's prebuilt bundle imports `roughjs/bin/rough`, which roughjs 4.6.4 no longer ships (`bin/` has `core.js`, `generator.js`, `math.js`, no `rough.js`). Webpack fails with `Module not found: … roughjs/bin/rough`. **Verified error.** Fix, verified working:

  ```ts
  // remotion.config.ts
  Config.overrideWebpackConfig((config) => {
    config.resolve.alias = {
      ...config.resolve.alias,
      'roughjs/bin/rough$': path.resolve('node_modules/roughjs/bundled/rough.esm.js'),
      'roughjs/bin/generator$': path.resolve('node_modules/roughjs/bin/generator.js'),
      'roughjs/bin/math$': path.resolve('node_modules/roughjs/bin/math.js'),
    };
    return config;
  });
  ```
- Importing the package root pulls the whole editor (React, jotai, radix, mermaid). It bundles and works, but it is ~3–5 MB of JS per bundle and the first bundle takes ~23 s. **Verified.**
- `@remotion/fonts` is a separate package; forgetting it fails with a confusing webpack resolution dump. **Verified.**

**Verdict.** Default. You are buying the patched capture path, the ffmpeg pipeline, the concurrency manager, `--frames` chunking for resume, and Remotion Studio as a free scrubber for reviewing cues against narration. All of those you would otherwise hand-roll.

### (2) Playwright / CDP frame capture

**Determinism — the recipe that works.** Do not run the page in real time at all. Every frame is `seekAnimation(t)` then screenshot. Verified byte-identical across separate Chromium processes:

```
--force-device-scale-factor=1 --force-color-profile=srgb --font-render-hinting=none
--disable-lcd-text --hide-scrollbars --disable-gpu --disable-threaded-animation
--run-all-compositor-stages-before-draw --deterministic-mode
```
Chromium 153 accepts all of them without complaint (**verified**). Three identical screenshots of the same seek are identical bytes; the same 5-frame hash sequence reproduces across two fresh `node` processes (**verified**).

`page.clock` (Playwright ≥1.45) is the *other* option — it fakes `Date`, `setTimeout`, `requestAnimationFrame`, `performance`, `Event.timeStamp` — but you do not need it if the page is a pure `setFrame(t)` function. Prefer the pure function; clocks are for pages you cannot modify.

**Linux headless.** Works with the system Chromium; no X, no sandbox flags needed beyond the usual. `--disable-gpu` is what makes it deterministic, and it is also what makes canvas/WebGL slow — irrelevant here since the scene is SVG.

**Throughput.** See table: 13–27 fps depending on scene weight; flat past 4 parallel pages. This is 20–25 % slower than Remotion's patched path and you own the muxing.

**Arabic.** Fine, but you must `await page.evaluate(() => document.fonts.ready)` after setting content and before frame 0, per page, or the first frames render in a fallback face. **Verified necessity in my harness; the failure mode itself was not reproduced.**

**Verdict.** Fallback and debugging harness. When an Arabic line looks wrong, this is where you inspect it, because you control the page.

### (3) Hybrid: `exportToSvg` per scene + CSS/SMIL in Chromium + capture

**Verified facts:**
- CSS/Web Animations seek is exact: `for (const a of el.getAnimations()) { a.pause(); a.currentTime = t; }` → deterministic, byte-identical across processes, different frames at different `t`.
- SMIL seek is exact: `svg.pauseAnimations(); svg.setCurrentTime(t)` drives `<animate>` on `stroke-dashoffset`, on a clip rect's `width`, and on a clip rect's `x`. Progressive, monotone frame hashes; LTR and RTL wipes converge to the same final frame. **Verified** (`smil-clip3.mjs`). Caveat: animated values are **not** visible through `getAttribute` — read pixels or computed style, never `getAttribute`, when debugging.
- The scene DOM is built once, so per-frame cost is 2 attribute writes per element. That is the 13.7 ms floor.

**What it buys you:** the SVG is a deliverable (open it in a browser, scrub it, mail it to a reviewer), and the frame loop is trivial. **What it costs you:** you author per-element `begin`/`dur` in SMIL or a Web Animations timeline, you still need a capturer, and you still need ffmpeg. The prior-art SMIL tool (excalidraw-animate) also cannot do Arabic text, as shown in §3.4 — so "use excalidraw-animate's output" is not on the table regardless.

**Verdict.** Not the default as a standalone. Use it *inside* option 1: Remotion renders a `<Scene>` whose only job is to mount the exported SVG once and seek it. You get the SVG artifact and the fast capture path.

### (4) Audio mux and frame lock

**Remotion path, verified:** `<Audio src={staticFile('narration.wav')} />` inside the composition, then `npx remotion render … --codec=h264`. Result: `h264 1920x1080 r_frame_rate=30/1 duration=3.000000 nb_frames=90`, audio `aac duration=3.008000`. Exactly 90 frames, video exactly 3.000 s. **Verified with ffprobe.**

The 8 ms of AAC padding (3.008 vs 3.000) is the encoder's frame granularity, not drift. It does not accumulate, because the audio is muxed once at the end from the original file.

**Manual path, for the fallback:**

```
ffmpeg -framerate 30 -i frames/%06d.png -i narration.wav \
  -map 0:v -map 1:a -c:v libx264 -crf 20 -preset slow -pix_fmt yuv420p \
  -r 30 -fps_mode cfr -c:a aac -b:a 192k -movflags +faststart -shortest out.mp4
```

`-fps_mode cfr` (ffmpeg ≥5, `-vsync cfr` before that) is the one flag people forget: without it a dropped capture frame silently retimes the whole film. `-shortest` guards against audio longer than video.

**Frame lock rule.** The narration is the clock *once*, in project metadata, and never during rendering. Scene boundaries and cues are integer frames computed from ms at edit time. If the generator ever reads a wall clock or an audio duration mid-render, determinism is gone.

**For chunked renders** (recommended: one chunk per scene or per 5-minute segment, so a failure costs minutes not half an hour), encode chunks with identical settings, then `concat` with `-c copy`. **Inferred** — standard x264 behaviour, not tested here.

## 5. Pipeline shape

```
board (scene_001.excalidraw)  +  cues (scene_001.cues.json)
        │
        ├── [build]  exportToSvg({elements, appState, files, skipInliningFonts})
        │              → scene_001.svg  (one <g> per element, frozen line breaks)
        │              → scene_001.geom.json  (per element: which paths are
        │                 stroke/fill/head, freedraw prefix-d tables, text bboxes)
        │
        ├── [render] Remotion composition <Animatic>
        │     frame f → find scene by frame range → scene SVG mounted once
        │     → per element: p = ease((f - cueFrame)/drawFrames)
        │        outline path: stroke-dashoffset = 1 - p
        │        text line:    clip rect width/x
        │        freedraw:     d = prefixTable[p * (K-1)]
        │     → Remotion capture → ffmpeg (h264, crf 20) + <Audio> narration
        │
        └── out.mp4   (1920×1080, 30/1, aac)
```

Contract between the two halves — keep it this small:

```ts
type ElementPlan = {
  id: string;
  cueFrame: number;
  drawFrames: number;
  reveal: 'dash' | 'clip' | 'prefix';
  nodes: string[];        // selectors inside the exported SVG
  direction?: 'rtl' | 'ltr';
};
type ScenePlan = { file: string; startFrame: number; frames: number; elements: ElementPlan[] };
```

The renderer never parses Excalidraw JSON. The builder never knows about Chromium. That seam is what lets you swap options 1 and 2 without touching the animation logic, and it is the part I would protect in review.

Commands actually used here:

```bash
# Remotion, one-time
npm i remotion@4 @remotion/cli@4 @remotion/fonts@4 react@19 react-dom@19
npm i @excalidraw/excalidraw@0.18.1
npx remotion browser ensure            # 98.9 MB headless shell, Chromium 157

# render (the whole film)
npx remotion render src/index.ts Animatic out.mp4 --concurrency=4 --codec=h264 --crf=20

# chunk, for resume
npx remotion render src/index.ts Animatic chunk-0.mp4 --frames=0-8999 --concurrency=4

# fallback capturer
node render.mjs --scene scene_001.svg --from 0 --to 899
```

## 7. What I did not establish

- Whether Remotion's headless shell 157 and the fork's text wrapping produce identical line breaks to the user's editor. The frozen-line-break design says it does not matter for *existing* boards, only for boards authored against a different font build. Worth one A/B test on a real Arabic board.
- Remotion's behaviour at `durationInFrames: 45000` (memory, progress granularity, ffmpeg pipe back-pressure). Not tested; chunking sidesteps it.
- Whether `exportToSvg`'s clip-path wrappers (frame/magicframe elements) break the `i`-th `<g>` ↔ `i`-th element mapping in practice. The code path exists; the animatic format probably should not use frames at all.
- Real per-scene element counts for this project. My 200-element scene is a guess; if scenes are 30–50 elements, expect ~20 ms/frame and ~15 min per full render.
